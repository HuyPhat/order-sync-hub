# Auth 5b: refresh tokens and login rate limit

Date: 2026-11-05. Follows 5a (users, login, access token, roles; PR #13).

## Goal

A client can keep a session for up to 7 days without storing the password: login also returns a
rotating refresh token, `POST /auth/refresh` swaps it for a new access token, `POST /auth/logout`
ends the session. Repeated failed logins get rate limited.

## Facts

- 5a is merged. `POST /auth/login` returns only `{ accessToken, expiresIn }` (HS256, 15 min).
- There is no `refresh_tokens` table, no rate limiter and no `trust proxy` setting; `req.ip` is the
  socket address.
- Node 24 has `randomBytes`, `createHash('sha256')` and `randomUUID`; no new dependency is needed for
  tokens.
- Integration tests revert and re-apply every migration, so a new table is covered automatically.

## Assumptions

- The React client may fire refreshes concurrently (several tabs, parallel requests that all get a
  401) and may retry immediately. Hence a grace window (approach C), not strict single-use. The
  client should still single-flight its refresh calls.
- A refresh token is 32 random bytes (base64url). That entropy makes a plain SHA-256 enough; no
  argon2.
- Access tokens stay valid for up to 15 min after logout (stateless). Accepted and documented.
- `/auth/refresh` and `/auth/logout` are public: the refresh token is the credential.

## Decisions

1. **Table `refresh_tokens`:** `id`, `userId` (FK, `ON DELETE CASCADE`), `familyId` (CHAR 36, indexed),
   `tokenHash` (CHAR 64, unique), `expiresAt`, `usedAt` (null), `revokedAt` (null), `createdAt`.
   Only the hash is stored.
2. **Rotation with grace (approach C):** the token row is read `FOR UPDATE` in a transaction, which
   serialises concurrent requests with the same token.
   - unknown, expired or revoked: 401.
   - never used: mark `usedAt = now`, issue a child in the same family.
   - used less than 10 s ago (`REFRESH_GRACE_SECONDS`): accepted again, issues another child, keeps the
     original `usedAt` so the window does not slide. The family then has more than one live token; the branches live on independently for the rest of the session and reuse across branches is not detected (accepted ceiling of approach C; a `parentId` column that revokes siblings would fix it).
   - used 10 s or more ago: reuse. Revoke the whole family (committed), answer 401.
3. **Each refresh re-reads the user**, so the new access token carries the current DB role. Each
   rotation gives the child a fresh 7 days (sliding, no absolute cap).
4. **Logout:** revoke the family of the given token; always 204, also for an unknown token.
5. **Rate limit:** `express-rate-limit` (memory store), 5 failed logins per IP+email per 15 min,
   `skipSuccessfulRequests: true` so successful logins are not counted. The limiter runs after body
   validation, so malformed requests do not count. The 6th failure and everything after it, even
   with the right password, gets 429 + `Retry-After` through the error handler. Successful logins are
   not counted but also do not clear earlier failures; the window does.
6. **Not now (go in CLAUDE.md known gaps):** the memory store resets on restart and is not shared
   across instances (switch to a Redis store in step 6/7); `trust proxy` is not set, so behind a
   reverse proxy all clients share one IP (set it at deploy, step 10); expired and used rows are never
   deleted (BullMQ job, step 6); no "logout everywhere".

## Acceptance criteria

1. Migration + model `RefreshToken`; an integration test checks the table and the cascade (deleting
   a user deletes the user's tokens).
2. `POST /auth/login` also returns `refreshToken` and `refreshExpiresIn: 604800`. The database holds
   only the SHA-256 hash; the raw token is never stored or logged.
3. `POST /auth/refresh { refreshToken }` returns `{ accessToken, expiresIn, refreshToken,
   refreshExpiresIn }`; the new token is in the same family; the access token carries the user's
   current DB role.
4. Unknown, expired or revoked token: 401 with one generic message.
5. A token used 10 s or more ago: 401 and the whole family is revoked (the newest token fails too).
6. A token used less than 10 s ago still works (new child), and does not revoke the family.
7. Two concurrent refreshes with the same token both get 200 and a different new token each; the
   family is not revoked.
8. `POST /auth/logout { refreshToken }`: 204; later refresh with any token of that family: 401; an
   unknown token also gets 204.
9. Rate limit: the 6th failed login for the same IP+email within 15 min gets 429 with `Retry-After`
   (also with the right password); it works again after the window (fake timers); successful logins
   do not count; another email is unaffected; unknown email and wrong password count alike; invalid
   bodies (400) do not count.
10. `TooManyRequestsError` -> 429 in `error-handler.ts`, body `{ status: 'error', message }`.
    Refresh/logout bodies are strict zod objects (400 on wrong type or extra key); 405 + `Allow:
    POST` on other methods.
11. `pnpm typecheck`, `pnpm format:check`, `pnpm test`, `pnpm test:integration` pass. CLAUDE.md is
    updated (status table, data model, API, architecture, planned work, known gaps).
